# TradePilot 策略回测开发

把策略想法落实为可运行、可验证、口径明示的回测。以实际交易规则和当前代码为准：动手前先读 `docs/backtest-development.md`（权威规范）、`python/task_registry.py` 和相关策略目录（含其 README.md），不要把历史策略的行为误当成新策略接口的默认行为。

技能分工：验证因子或信号有效性用项目级 `factor-research` 技能；对已有运行结果做归因复盘用 `strategy-result-review` 技能；本技能管中间的「把想法写成交易规则并跑通」。

## 第一步：识别任务类型

- **解释已有策略**：查阅 `python/strategies/<id>/`（runner.py / strategy.py / README.md）、`python/task_registry.py` 的注册信息和 `latest-report.md`，复述交易标的及候选范围、信号定义与产生时点、买卖时点与成交口径、仓位与资金分配、止盈止损、费用及运行命令。区分代码当前行为、文档描述和用户拟议的改动；只要求解释时不擅自改代码。
- **设计或修改策略**：先检查现有实现与可用数据（`data/backtest_data/`），再把用户想法写成可执行规则。只追问缺失且会改变交易结果的规则，其余给出合理建议供用户选择；不要默默替重大歧义设默认值。
- **由因子研究转策略**：先核对研究的样本区间、收益标签定义（未来几个交易日、从什么价格起算、复权口径）、观察时点和局限，再建议因子充当入场、过滤、排序还是退出条件。研究中的相关性或远期收益不等于按真实成交规则可获得的策略收益——信号延迟、成交时点、费用和 T+1 都会侵蚀它。

## 第二步：确定规则清单

编码前把以下规则逐项写下来并与用户对齐（只追问会改变交易结果的缺失项）：

- 交易标的及候选范围（单股 / ETF / 组合）
- 评分或排序算法（因子转策略时即因子如何变成排序分）
- 买入与卖出信号；信号所用数据及产生时点（当日收盘后可知还是盘中可知）
- 成交时点与执行口径（当日收盘理想化还是次日开盘；是否启用 `enforce_t1`）
- 仓位与资金分配、止盈止损
- 费用口径（`FeeConfig.stock_legacy()`、`etf_legacy()` 还是自定义）
- 回测区间与比较基准

这份清单同时就是策略目录 README.md 的骨架（见第五步），确认过程即写文档过程。

## 第三步：引擎能力核对与编码

先核对引擎能力再编码，不默默假设引擎已支持所需规则。

- 新事件引擎在 `python/backtest/engine.py`：策略实现 `on_bar(StrategyContext) -> list[OrderIntent]`。上下文只含当根及以前可见信息和只读持仓快照；订单最早在下一根可交易 K 线开盘成交。账户和费用由 `Engine`、`FeeConfig` 负责，新策略里不直接扣现金。最小策略示例见 `docs/backtest-development.md`。
- **引擎已支持**：可选 `enforce_t1`（T+1 卖出限制）、`CashBuyIntent`（按可用现金和一手整数倍买入）、`SellAllIntent`（整笔清仓）、分红/拆分记账。用法参照 `python/strategies/amv_below_ma_defensive_etfs/`。
- **仍未模拟**：停牌/涨跌停对成交的约束、盘口容量。策略依赖这些规则时，先明确所需数据和成交处理方案并向用户说明，再决定如何扩展；不能据此把旧策略无差别迁入新引擎。
- 前视偏差红线：信号只能使用生成时已可见的数据，订单不能以信号产生前的价格成交。
- 目录职责：正式策略放 `python/strategies/<id>/`，可复用指标放 `python/factors/`，通用成交与记账留在 `python/backtest/`；临时实验放研究目录，不塞回 `python/backtest/`。
- 统一入口：需要统一命令运行时，在 `python/task_registry.py` 以 `TASKS[("strategy", task_id)] = TaskSpec(...)` 显式注册任务名、数据源、默认费用、执行口径与 handler，并在 `python/tests/backtest/` 补充测试。
- 旧策略改造：旧策略可能沿用理想化成交时点（如 `amv_winning` 的「收盘后才能确定的信号按同日收盘成交」，manifest 标注 `legacy_same_close_idealized`，不可当作可实盘复制的收益）。修改时不要顺手改变其历史口径；确要改成交或费用规则，须单独做收益对照（见第四步）。

## 第四步：验证

**新策略**：

1. 用小型确定性样例（手工算得出结果的几根 K 线）核对信号时序、成交价量、仓位、费用和止盈止损。
2. 跑测试与格式检查：

   ```bash
   /home/wang/python_env/B1_RATE/bin/python -m pytest -q python/tests
   git diff --check
   ```

3. 用统一入口核对注册并跑一个有代表性的区间：

   ```bash
   ./scripts/backtest.sh list strategies
   ./scripts/backtest.sh run strategy <名称> --start YYYYMMDD --end YYYYMMDD
   ```

4. 检查运行产物和 `run_manifest.json`：数据源、配置快照、费用、`execution_mode` 与运行状态。

**改造或迁移旧策略**：动手前先固定相同数据、日期、配置及费用下的逐笔交易和 NAV 基线。改成交或费用规则时逐笔列出差异（价格、数量、费用、现金路径），不只比较最终收益——费用参数可能改变买入数量和后续整条路径。基线对照样本至少覆盖有交易、空仓、止损及缺失行情四类情形。研究类任务需断言实际观察日期落在用户请求区间，不能只查 manifest。

**latest-report.md 机制**：只有 `./scripts/backtest.sh run` 成功后才更新任务源码目录的 `latest-report.md`；失败运行不覆盖上一份成功报告；直接运行单个脚本不更新。验证时若直跑过脚本，需再走一次统一入口。

## 第五步：交付

- 策略目录配 README.md，说明交易规则、执行口径、费用、数据要求及与基线的差异——第二步的规则清单直接落进来。这是项目惯例，缺失会让复盘技能无法建立「退出原因 → 代码分支」的映射。
- 交付说明写清：结果可复现的范围（数据、区间、配置）、尚未建模的交易限制（停牌、涨跌停、盘口容量）、可能夸大收益的假设。
- 停止维护的正式策略在 `python/task_registry.py` 标 `archived`：源码留在受 Git 管理的策略目录，不出现在默认 `list`。
- 收尾指路：跑出结果后要归因盈亏、找优化方向 → 用 `strategy-result-review` 技能复盘；要验证新信号有效性 → 回 `factor-research` 技能。

## 注意事项

- **口径一致性**：跨策略比较时核对 `execution_mode` 与年化口径；不同区间、不同费用的运行不可直接比收益。
- **区分代码行为与拟议改动**：向用户复述的是当前代码的实际行为；「应该怎么改」单独列出并等确认。
- **不默默假设引擎能力**：新策略需要的每条交易限制（T+1、涨跌停、最小单位、停牌），要么确认引擎已有对应参数，要么明示为未建模并向用户提示影响。
- **理想化口径警告**：`legacy_same_close_idealized` 类结果必须注明属理想化假设，不宣称可实盘复制，不宣称保证盈利——结论只对本次数据、区间和配置成立。
- 需要用户授权的改动（改口径、改费用、迁移）先列方案再动手。
