# TradePilot 策略结果复盘

读 `data/backtest_runs/<运行>/` 的结果和对应策略源码，逐笔归因盈亏，产出复盘报告与优化建议。

这是一次**只读诊断**：不改策略代码、不重跑回测。诊断完之后，把建议落地是另外两个技能的事——需要验证新因子/新信号时用 `factor-research`，需要改策略规则或加过滤时用 `strategy-backtest-development`。这样分工的好处是复盘不会被"顺手改一点代码看看"带偏，结论先行、可追溯。

结果格式按任务而异（`docs/backtest-development.md` 明确不统一），所以先摸清这次运行到底产出了什么，再动手分析。

## 第一步：定位运行与结果

优先读运行目录的 `run_manifest.json`，它给出 `task_id`、请求区间、费用、`execution_mode`（成交口径）和运行状态，是判断结论能否成立的第一手依据。没有清单时，用目录名 `<task_id>__<时间>__<标识>` 反查任务，或看 `python/strategies/<task_id>/latest-report.md` 里记录的当次运行路径。

留意两类容易踩坑的目录：多阶段任务（如 `etf_amv`）把真实结果放在 `oos/` 等子目录，顶层只有清单；个别任务（如 `amv_winning_defensive`）会同时写多个 `trades_*.csv`，要确认分析的是哪一个，别把分支结果当成主结果。

## 第二步：跑统计脚本

```bash
~/python_env/B1_RATE/bin/python .claude/skills/strategy-result-review/scripts/analyze_run.py <运行目录> [<运行目录2> ...]
```

脚本会自适应各种结果形态：三种 `trades.csv` 列结构（配对式 / 事件流水式 / `(no_trades)` 空表）、单腿与多腿 `nav.csv`、`metrics.json` 缺失时从净值推导指标。它输出整体指标、回撤区间、盈亏集中度、按退出原因/年份/持仓天数/标的的分组统计，以及最赚最亏各 N 笔（`--top N`，默认 15；`--trades` 输出全部逐笔）。

脚本只给**客观统计**，不做归因——"`hard_stop_2.5pct` 亏了 32 笔"是它的事，"这个止损是不是设得太紧"是下一步的事。先看 `warnings` 字段，它会说明哪些指标是推导的、哪些数据缺失，这决定了后面结论的置信度。

分组统计里最值得先看的是 `by_exit_reason`：它把总盈亏拆到了每类退出规则上，通常一眼就能看出钱是从哪条规则漏出去的。

## 第三步：读源码，建立"退出原因 → 代码分支"的映射

到 `python/strategies/<task_id>/`（`runner.py` 或 `strategy.py`）里，把 `sell_reason`、`buy_signal_type` 的每个取值定位到具体代码分支，连同该分支的阈值、触发条件和成交时点一起记下来。

**这一步是复盘和"跑个统计"的分水岭。** 没有它，报告只能重复脚本已经算过的数字，说不出任何用户自己看不出来的东西。标准是：报告里每提到一类交易，都能指向代码里的具体行和它背后的交易假设。

顺带核对成交口径：`execution_mode` 为 `legacy_same_close_idealized` 之类时，信号按当日收盘成交，属理想化假设，结果不可当作可实盘复制的收益。

## 第四步：归因与归纳

按顺序过一遍，每一步都落到"哪个规则、什么条件、多少钱"：

1. **整体**：收益、回撤、夏普对基准；写明年化口径（不同任务不一致，见下）。
2. **按退出原因**：哪类退出是主要亏损来源、哪类是主要盈利来源；对照第三步的代码，判断阈值是偏紧还是偏松。例如止损类退出占了绝大多数亏损且平均持仓很短，多半是止损位被正常波动打穿，而不是判断错了方向。
3. **按年份**：哪几年失效；把失效年份和当时的市场环境对上（可用 `nav.csv` 的 `benchmark_nav` 列看基准同期表现）。
4. **按持仓天数**：是否存在"过早止损"或"扛太久"的分段特征。
5. **逐笔抽样**：取最赚和最亏各几笔，说清这笔在代码里由哪个条件触发、当时的价格与信号长什么样。抽样要覆盖各类退出原因，不能只看极端值。
6. **归纳**：写 3-5 条可证伪的规律，每条都要能回答"如果这条是对的，改什么、预期看到什么变化"。

归因要克制：样本量小的分组（个位数交易）下的结论标为待验证，不要把噪声说成规律。

## 第五步：写复盘报告

单次复盘写 `<运行目录>/review.md`（与本次运行数据放在一起，不随 Git 提交）。横向对比写 `data/backtest_runs/_reviews/<YYYY-MM-DD>-<描述>.md`，这类目录需要时新建。

报告用这个结构：

```markdown
# <策略名> 复盘：<区间>

## 执行口径与数据来源
运行目录、task_id、区间、执行口径、费用、指标来源（metrics.json 还是从 nav 推导）

## 收益与风险总览
策略 vs 基准的收益/年化/回撤/夏普/交易数/胜率/盈亏比/持仓/暴露

## 退出原因分布与盈亏贡献
每类退出的笔数、胜率、平均盈亏、总盈亏贡献，以及对应的代码分支

## 年度表现
逐年的交易数、胜率、平均盈亏，标出失效年份

## 分组特征
持仓天数分段、买入信号类型、标的维度的表现差异

## 逐笔典型案例
最赚/最亏各几笔，说清在代码里怎么触发

## 归因结论
3-5 条可证伪的规律，每条附支撑数据

## 优化建议
分「可立即验证」与「需先研究」两档；每条注明落到哪个技能
（改规则 → strategy-backtest-development；验证新信号 → factor-research）

## 局限与未建模项
数据区间、理想化成交假设、未建模的交易限制、小样本分组
```

优化建议是这份报告的交付物，所以每条都要具体到可以执行：指出改哪个阈值或哪条规则、方向是什么、预期改善哪个指标，而不是"建议优化止损"。同时要说明这条建议是数据直接支持的，还是需要先用 `factor-research` 验证的假设。

## 注意事项

- **年化口径不统一**：`amv_winning` 系按 365 自然日折算，`python/backtest/metrics.py` 按 243 交易日折算。跨策略比较年化时要标明口径，必要时统一重算。
- **区间不一致不能比**：不同运行的回测区间往往不同，直接横向比收益会得出错误结论；脚本的 `comparison.notes` 会提示这一点。
- **区分代码行为与账面数字**：说明的是当前代码的实际行为，不要顺手评价"应该怎么写"——那是 `strategy-backtest-development` 的职责。
- **不宣称保证盈利**：回测含理想化假设，结论只对本次数据、区间和配置成立。
- 每条结论都要能指回具体交易或代码行；指不回去的，就不要写进报告。
